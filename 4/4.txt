MongoDB 기초 및 개념
1. MongoDB는 어떤 유형의 데이터베이스이며, 어떤 형식으로 데이터를 저장합니까? MongoDB의 스키마 특성에 대해 설명하세요.

MongoDB는 NoSQL 유형의 데이터베이스로, 
문서 지향(Document-Oriented) 방식으로 데이터를 저장합니다. 
데이터를 JSON과 유사한 형식인 BSON(Binary JSON) 형식으로 저장하여, 
비정형 데이터를 효율적으로 관리할 수 있습니다. 

MongoDB는 스키마리스(Schemaless) 특성을 가지므로, 
데이터를 저장할 때 고정된 스키마가 필요하지 않습니다. .

2. MongoDB에서 문서(Document)와 컬렉션(Collection)의 개념을 설명하고, SQL에서 테이블(Table)과의 차이점을 비교하세요.

문서(Document): MongoDB에서 데이터의 기본 저장 단위로, 
키-값 쌍으로 구성된 JSON 형식의 객체입니다.

컬렉션(Collection): 여러 문서들을 그룹화하는 MongoDB의 논리적 단위로, 
SQL의 테이블(Table)과 유사합니다.

컬렉션은 SQL 테이블과 달리 MongoDB 컬렉션은 서로 다른 구조를 가진 문서들을 저장할 수 있어, 
고정된 스키마가 필요하지 않습니다. 

3. MongoDB에서 스키마리스(Schemaless) 데이터베이스의 장점과 단점을 설명하세요.

장점:
유연성: 데이터 구조를 사전에 정의할 필요가 없으며, 필요에 따라 데이터 구조를 쉽게 변경할 수 있습니다.
빠른 개발: 데이터를 유연하게 저장할 수 있어 개발 초기 단계에서 데이터 모델링에 대한 부담이 줄어듭니다.

단점:
데이터 무결성 문제: 고정된 스키마가 없기 때문에 잘못된 데이터 구조로 인해 데이터 무결성이 저하될 수 있습니다.
복잡한 쿼리: 문서의 구조가 서로 다를 경우 복잡한 쿼리가 필요할 수 있습니다.

4. MongoDB의 주요 특징 중 수평적 확장성에 대해 설명하고, 샤딩(Sharding)이 어떻게 수평적 확장을 지원하는지 서술하세요.

MongoDB는 수평적 확장성(horizontal scalability)을 지원하여, 서버 자원을 추가함으로써 데이터베이스의 용량과 성능을 확장할 수 있습니다. 

수평적 확장은*샤딩(Sharding)을 통해 구현됩니다. 샤딩은 데이터를 여러 서버(샤드)로 나누어 저장하고, 쿼리 라우터가 각 샤드로 쿼리를 분배합니다. 
이를 통해 대규모 데이터를 처리할 수 있으며, 트래픽과 저장소의 부담을 분산시킵니다.

5. MongoDB에서 BSON(Binary JSON) 형식이 사용되는 이유와 이 형식의 주요 특징에 대해 설명하세요.
BSON은 Binary JSON의 약자로, MongoDB에서 데이터를 저장하고 전송할 때 사용하는 바이너리 형식입니다. 

BSON이 사용되는 이유는 다음과 같습니다:
빠른 읽기 및 쓰기 성능: 바이너리 포맷은 빠른 데이터 처리 속도를 보장합니다.
다양한 데이터 유형 지원: BSON은 날짜, 정수, 부동 소수점 등 다양한 데이터 유형을 지원합니다.
크기 효율성: 데이터를 바이너리로 직렬화하여 저장 공간을 효율적으로 사용합니다.

MongoDB 트랜잭션 관련
1. MongoDB에서 멀티 도큐먼트 트랜잭션(Multi-Document Transaction)이 무엇이며, 어떻게 작동하는지 설명하세요.

멀티 도큐먼트 트랜잭션은 여러 문서를 포함하는 작업을 하나의 트랜잭션으로 묶어 처리하는 기능입니다. MongoDB에서 여러 컬렉션이나 데이터베이스에 걸쳐 원자적(Atomic)으로 실행되는 작업을 보장합니다.
트랜잭션은 시작되고, 커밋하거나 롤백할 수 있습니다.

2. MongoDB 트랜잭션의 ACID 속성(Atomicity, Consistency, Isolation, Durability)에 대해 설명하고, 각 속성이 트랜잭션에서 어떤 역할을 하는지 서술하세요.

Atomicity(원자성): 트랜잭션 내의 모든 작업이 모두 성공하거나, 실패 시 아무 작업도 반영되지 않는 것을 보장합니다.

Consistency(일관성): 트랜잭션이 완료되면 데이터베이스는 일관된 상태를 유지해야 합니다.

Isolation(고립성): 여러 트랜잭션이 동시에 실행될 때, 서로 간섭 없이 독립적으로 실행됩니다.

Durability(내구성): 트랜잭션이 커밋되면 그 결과는 영구적으로 저장되어 서버가 갑작스럽게 중단되어도 데이터가 손실되지 않습니다.

3. MongoDB 트랜잭션 사용 시, 데이터 일관성을 보장하기 위해 사용하는 commitTransaction()과 abortTransaction() 메서드의 역할을 설명하세요.

commitTransaction(): 트랜잭션을 성공적으로 종료하고, 트랜잭션 내의 모든 변경사항을 데이터베이스에 반영합니다.

abortTransaction(): 트랜잭션을 취소하고, 트랜잭션 내의 모든 변경사항을 롤백합니다.

4. MongoDB에서 트랜잭션을 사용할 수 있는 환경을 설명하고, 단일 인스턴스에서 트랜잭션이 가능한지 여부를 기술하세요.

MongoDB 트랜잭션은 복제 세트(Replica Set)나 샤드 클러스터(Sharded Cluster) 환경에서 사용할 수 있습니다. MongoDB 4.0부터는 단일 인스턴스(Standalone)에서도 트랜잭션을 지원합니다. 단일 인스턴스에서도 멀티 도큐먼트 트랜잭션을 사용할 수 있습니다.

5. MongoDB에서 트랜잭션을 구현한 예시 코드를 제시하고, 각 단계별로 동작 방식을 설명하세요.

const session = await client.startSession();
session.startTransaction();

try {
  await collection1.insertOne({ name: "Alice" }, { session });
  await collection2.updateOne({ name: "Bob" }, { $set: { age: 30 } }, { session });
  
  await session.commitTransaction();
  console.log("Transaction committed.");
} catch (error) {
  await session.abortTransaction();
  console.error("Transaction aborted due to error:", error);
} finally {
  session.endSession();
}

트랜잭션 시작: session.startTransaction()을 통해 트랜잭션이 시작됩니다.
작업 수행: 여러 컬렉션에 걸쳐 문서를 삽입하거나 업데이트하는 작업이 트랜잭션 내에서 수행됩니다.
커밋: 모든 작업이 성공적으로 완료되면 commitTransaction()으로 트랜잭션을 커밋하여 변경사항을 반영합니다.
롤백: 작업 중 오류가 발생하면 abortTransaction()을 호출하여 변경사항을 취소합니다.
세션 종료: endSession()을 통해 세션이 종료됩니다.


샤딩(Sharding) 관련

1. MongoDB에서 샤딩(Sharding)이란 무엇이며, 이를 통해 데이터베이스 성능을 어떻게 최적화할 수 있는지 설명하세요.

샤딩(Sharding)은 데이터를 여러 샤드(Shard)에 분할하여 저장함으로써 대용량 데이터를 처리하는 MongoDB의 수평 확장 기술입니다. 이를 통해 하나의 서버에 집중되는 부하를 분산하고, 더 많은 데이터를 저장할 수 있으며, 쿼리 성능을 개선할 수 있습니다.

2. MongoDB에서 샤드 키(Shard Key)의 역할과, 샤드 키를 선택할 때 고려해야 할 요소들을 설명하세요.

샤드 키(Shard Key)는 데이터를 샤드에 분산할 기준이 되는 필드입니다. 샤드 키는 균형 잡힌 데이터 분포를 유지하고, 쿼리 성능에 영향을 미치므로 신중하게 선택해야 합니다. 고려해야 할 요소로는 카디널리티(다양한 값의 수), 쿼리 패턴, 데이터의 균등한 분산 등이 있습니다.

3. MongoDB에서 샤딩 구조의 주요 구성 요소(샤드, 쿼리 라우터, 컨피그 서버)를 설명하고, 각 구성 요소가 어떻게 상호작용하는지 서술하세요.

샤드(Shard): 데이터가 저장되는 실제 서버입니다.
쿼리 라우터(Query Router): 클라이언트 요청을 적절한 샤드로 라우팅하는 역할을 합니다.
컨피그 서버(Config Server): 샤딩 메타데이터와 샤드의 구성 정보를 저장합니다.
쿼리 라우터는 클라이언트의 요청을 받아 컨피그 서버에서 샤드 분할 정보를 조회한 후 적절한 샤드로 요청을 전달합니다.

4. MongoDB에서 Range-based Sharding과 Hash-based Sharding의 차이점을 설명하고, 각각의 장단점을 비교하세요.

Range-based Sharding: 샤드 키 값을 기준으로 범위에 따라 데이터를 나누는 방식입니다.

장점: 특정 범위에 대한 쿼리가 효율적입니다.
단점: 샤드 간 데이터 불균형이 발생할 수 있습니다.
Hash-based Sharding: 샤드 키 값을 해시하여 데이터를 균등하게 분산합니다.

장점: 데이터가 고르게 분산되어 샤드 불균형이 적습니다.
단점: 범위 기반 쿼리의 성능이 떨어질 수 있습니다.

5. MongoDB에서 샤딩의 장점과 단점을 설명하고, 샤딩이 적합한 상황과 그렇지 않은 상황에 대해 논하세요.

장점:
대용량 데이터 저장 및 처리
서버 부하 분산
수평 확장성 제공

단점:
시스템 복잡성 증가
관리와 운영 비용 상승
샤딩이 적합한 상황은 데이터가 매우 크고, 트래픽이 많은 경우이며, 소규모 애플리케이션이나 단일 서버로 충분한 처리량이 가능한 경우에는 샤딩이 필요하지 않습니다.

레플리카 세트(Replica Set) 관련
1. MongoDB에서 레플리카 세트(Replica Set)란 무엇이며, 이 기능을 사용하는 주된 목적에 대해 설명하세요.

레플리카 세트(Replica Set)는 동일한 데이터를 여러 서버에 복제하여, 데이터의 고가용성과 장애 복구를 보장하는 기능입니다. 주된 목적은 장애 발생 시 자동으로 다른 서버로 페일오버(Failover)를 통해 시스템의 연속성을 유지하는 것입니다.

2. MongoDB 레플리카 세트의 구성 요소인 Primary, Secondary, Arbiter의 역할과 동작 방식을 설명하세요.

Primary: 모든 쓰기 작업이 수행되는 주 서버입니다.
Secondary: Primary의 데이터를 복제하며, 읽기 작업을 처리할 수 있습니다.
Arbiter: 투표권을 가짐으로써 Primary 서버가 장애 발생 시 새로운 Primary 선출에 도움을 줍니다. Arbiter는 데이터를 저장하지 않습니다.

3. MongoDB에서 레플리카 세트를 사용하는 경우, Primary 서버에 장애가 발생했을 때 어떤 과정으로 장애를 복구하는지 서술하세요.

Primary 서버에 장애가 발생하면, Secondary 서버 중 하나가 투표를 통해 Primary로 승격됩니다. 이 과정은 자동으로 이루어지며, 서비스가 지속됩니다.

4. MongoDB에서 Secondary 서버를 활용한 읽기 작업 분산이 무엇인지 설명하고, 이 방법이 읽기 성능에 어떤 영향을 미치는지 논하세요.

Secondary 서버는 Primary 데이터를 복제하여 읽기 작업을 처리할 수 있습니다. 이를 통해 읽기 작업을 분산하여 성능을 향상시킬 수 있지만, 데이터의 일관성에 주의해야 합니다. Primary와 Secondary 간의 데이터 복제에는 지연 시간이 있을 수 있습니다.

5. 레플리카 세트와 샤딩의 차이점을 설명하고, 두 기능을 함께 사용할 경우의 장점에 대해 서술하세요.

레플리카 세트는 데이터의 고가용성과 장애 복구를 목적으로 합니다.

샤딩은 데이터를 여러 서버에 분산하여 대용량 데이터를 처리하고 수평적 확장성을 제공합니다.

두 기능을 함께 사용하면, 대규모 데이터 처리와 고가용성을 동시에 보장할 수 있습니다.
